# CLAUDE.md

Clinic AI Platform lets EU/EEA clinics (ADR-0020) answer patient messages in seconds using an
AI assistant grounded in that clinic's own data. It turns those conversations into
booked appointments instead of a human receptionist doing it manually.

These limitations are recorded rather than resolved. Production has no active staff identity by design, so the authenticated production click-through for P3-B and P3-C is deferred — a limitation of the validation surface, not an open implementation defect. `scripts/provision-clinic.ts` had not been run against production as of the recorded project status on 2026-10-08; this has not been re-verified since, so the full invitation cycle with a real owner is not proven in production. Any production run of it requires a separate explicit Owner decision. Slice 1B's implementation and production migration gates are closed; its authenticated production click-through is a documented deferred verification gap for the same reason: scripts/seed.ts hardcodes `DEMO_STAFF_ROLE` as a fixed exported `'receptionist'` constant, while both Slice 1B endpoints (`POST /api/knowledge-documents`, `POST /api/knowledge-documents/:id/complete`) require `owner` or `admin`, so the documented deployment-validation seed cannot produce a usable test identity. The alternative — manual role elevation of a publicly-published identity, a new production credential, and two permanent artifacts the application has no path to delete — was ruled against by the owner on all three counts. The first legitimate clinic onboarding will be the real verification. The same applies to #79's PDF signature check, tested only against a faked S3 client: read permission for the production storage key, Scaleway's handling of `Range` and `If-Match` on GET, and the HeadObject ETag are unverified. What is proven instead: credentials were verified during provisioning; the bucket is private; CORS was verified by reading it back; there is no lifecycle rule; both endpoints return 401 unauthenticated in production; migration 0014's privilege state was verified (SELECT and INSERT true, UPDATE and DELETE false, RLS and FORCE RLS unchanged); at the time of #79, 319 tests plus typecheck, lint, build and format:check were green; and the presigned Content-Type signature binding is covered by a regression test. docs/operations/production-rebuild-runbook.md is written but has never been executed or rehearsed.

Backups are not proven. A complete logical backup has not been demonstrated with the current database role and RLS configuration: under FORCE ROW LEVEL SECURITY, a role without BYPASSRLS may fail to dump protected tables or, with `--enable-row-security`, dump only the rows it can access, potentially omitting data. Production recovery therefore currently relies on Render's point-in-time recovery (3-day window). No restore of production has been tested, and backup completeness remains unassessed. A read-only restore-check tool exists only locally (not in this repository); it is not approved for use against production, Render or a PITR copy, and its passing is not evidence that a backup is complete. A local restore rehearsal (2026-10-19, synthetic data, physical copy) and its restore-check v10.3 results are recorded in `docs/operations/restore-drill-plan.md`; the Render PITR drill (Phase 3 there) has not started.

`clinic_ai_platform_user` (the migration and table-owner role; the application connects as `app_user`; since the credential rotation recorded in #113 the only login Render offers is `clinic_ai_platform_user2`, a member of `clinic_ai_platform_user`, and migrations execute with `current_user = clinic_ai_platform_user`) used to inherit `auth_bootstrap` and `invitation_acceptor`, so it could read the `staff_members`, `staff_sessions` and `invitations` rows of every clinic; `app_user` was never affected. Production's role also holds memberships Render created: rows granted by `postgres` with ADMIN only (`INHERIT FALSE, SET FALSE`) in `app_user` and the three function-owner roles, and inheriting memberships in `pg_read_all_stats` and `pg_signal_backend`; none of them gives inherited access to the three function-owner roles. After 0019, a migration that replaces one of the four SECURITY DEFINER functions must `SET LOCAL ROLE` to the function's owner for that statement only and then restore the previously executing role, never leaving the switch active until the runner's COMMIT (ADR-0025).

## Hard rules

- Nothing gets built before the roadmap phase that calls for it.
- No ADR changes status (Proposed → Accepted, etc.) without a human comment in the
  pull request saying so.
- Humans merge. Agents open pull requests; they never merge them.
- No real patient or clinic data anywhere — not in the repo, fixtures, issues, Notion,
  or an AI prompt.
- A one-way-door decision gets its own ADR, with Ahmed's approval, before code.
